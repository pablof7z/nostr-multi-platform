# Typed Projections and Overlay Pattern

## Typed Projections

The typed-projections migration uses the overlay-over-fallback pattern on both iOS and Android. The snapshot transport has completed the JSON-to-FlatBuffers migration (ADR-0037 Wave C), emitting both a typed sidecar and the legacy generic serde_json::Value tree from the same accessor calls within the same tick to prevent divergence. When payload:Value is deleted, the generic fallback branches become dormant dead code (harmless since every rendered key is fully populated by its typed decoder). SnapshotEnvelope carries Tier-3 fields (rev, running, last_error_toast, last_error_category, metrics, relay_statuses) and is the public decode API for envelope-level data, replacing the old generic Value tree. The SnapshotEnvelope API exposes decode_snapshot_envelope/decode_snapshot_typed_projections as pub for in-process Rust shells. Every snapshot projection must have a typed FlatBuffer representation in the sidecar (or typed SnapshotFrame fields) before payload:Value can be deleted. Every consumer (Chirp, Podcastr, tenex-off) must read the typed path for every key it uses, with no consumer referencing snapshot.payload or projections.<x>, before payload:Value deletion. The dynamic registry path (SnapshotRegistry::register/run, KernelSnapshot::projections, snapshot_projections_with_publish_cluster, encode_snapshot_value) must have no remaining producer before payload:Value deletion. The safe migration sequence per projection is: (1) add register_typed (additive, both paths live), (2) consumers switch to typed decoder, (3) remove that key's dynamic producer + SNAPSHOT_PROJECTIONS registry entry + regenerate, then after all keys: delete payload:Value. crates/nmp-codegen/src/swift_projections_registry.rs serializes step-3 (registry-entry removal) across all projections because every consumer-flip edits it. crates/nmp-app-template/src/runtimes.rs serializes the nip17 dm_inbox/dm_relay_list + nip57 zap_subscription registrations because they collide on one file. The AppHost trait lacked register_typed_snapshot_projection, blocking protocol-crate projections from the typed path; a prerequisite PR was needed to mirror the generic seam to the trait + both impls (nmp-ffi and nmp-app-template/builder.rs). The register_typed_snapshot_projection seam on AppHost mirrors the generic register_snapshot_projection signature with F: Fn() -> Option<TypedProjectionData> + Send + Sync + 'static. Tier-2 kernel built-ins use direct emission via Kernel::builtin_typed_projections rather than the SnapshotRegistry closure path, because built-ins read live &self kernel state. A collision-resolution step (merge_builtin_typed_projections) mirrors the documented JSON rule that built-in keys win, required because the iOS consumer matches by first key. The Tier-2 drain-on-emit keys (action_results, signed_events, action_stages, action_lifecycle) must capture their value ONCE at the JSON-insertion site into a per-tick Kernel field, because builtin_typed_projections runs after the JSON builder where the data is already drained. nmp.nip57.zaps and nmp.follow_list have .fbs schemas and encode/decode codecs but no live typed producer call site (their JSON producer is registered by Chirp's out-of-repo Rust shim). NMP must keep emitting JSON until both Podcastr and tenex-off bump to a dual-emitting rev and switch to typed, because decode_update_frame requires payload(). The FlatBuffers typed-projection registry reached 30/31 Swift readers after the iOS binding sweep, with nmp.feed.home having a dedicated TypedHomeFeedDecoder path. Chirp reads the entire generic payload tree via FlatBufferValueDecoder into one KernelUpdate Swift struct (KernelUpdateFrameDecoder.swift:56), and every key in SNAPSHOT_PROJECTIONS becomes a generated optional field in KernelTypes.generated.swift. Android's KernelUpdateFrameDecoder.kt gated the entire decode on snapshot.payload (which was no longer emitted) and built the whole KernelUpdate from the payload JSON map, making the app completely dark at v0.3.0 after payload:Value was deleted from the wire; the typed sidecars from PR #1074 were supplements, not a replacement. (Previously: Android was mentioned only as sharing the overlay-over-fallback pattern without noting the payload gate failure.) The Android fix rebuilds KernelUpdateFrameDecoder to decode the entire KernelUpdate from Tier-3 typed fields (rev, running, lastErrorToast from snapshot fields; metrics and relayStatuses from new decodeMetricsFromTier3/decodeRelayStatusesFromTier3; projections from typed sidecars only with no payload fallback), with a real-kernel-frame golden fixture test (KernelUpdateFrameDecoderTier3GoldenTest) that loads a Rust-emitted FlatBuffers hex fixture and asserts non-default values on every Tier-3 field, validating the new path and failing on the pre-fix decoder. The claimed_profiles decode cluster (CLAIMED_PROFILES_SCHEMA_ID, ClaimedProfilesModel, decode_claimed_profiles) was promoted to the public typed surface as part of the legacy {1,6} deletion migration, following the decode_claimed_events precedent. Podcastr never touches FlatBuffers in Swift; its own Rust crate (nmp-app-podcast) decodes the frame to a JSON envelope string that Swift parses with JSONSerialization. podcast-player has no Kotlin-side UpdateFrame/payload decoder; the binary frame is decoded in Rust via nmp_app_podcast_decode_update_frame (already migrated to the typed SnapshotEnvelope) and delivered via mpsc channel to Kotlin nativeNextUpdate, so no Tier-3 Kotlin rebuild was needed. podcast-player still has a pre-existing latent push-path bug where SnapshotCodec.decodeEnvelope decodes the envelope v as a bare PodcastSnapshot — a shape the wire never carried — the same defect class as NMP #1084. tenex-off reads exactly two keys from the JSON Value: projections.action_results and projections.publish_queue. nmp_core::typed_projections exposes public decode functions (decode_action_results, decode_publish_queue) with DTOs and SCHEMA constants for out-of-tree Rust consumers like tenex-off. The typed Swift decoder codegen (nmp gen typed-decoders) generates lookup+decode glue only for keys with a checked-in flatc --swift reader binding; the FlatBuffer wire to Chirp domain type mapping is hand-written (TypedProjectionGlue). The consumer switch must serialize SNAPSHOT_PROJECTIONS deletions (one PR per small batch) because every key deletion edits the single swift_projections_registry.rs file and its size-lock test. ProfileCard is shared across profile/claimed_profiles/resolved_profiles schemas and must use a flatc include (profile_card.fbs) to avoid triple-declaring nmp_kernel_ProfileCard in Swift. The per-key consumer flip recipe is: (1) flatc --swift binding, (2) Typed<Key>Decoder via codegen, (3) TypedProjectionGlue hand-written mapping, (4) KernelBridge decode, (5) KernelModel @Published slot + apply(), (6) KernelModel+Projections accessor typed-first with JSON fallback, (7) internal-consumer audit to avoid split-brain. Chirp's extractFlatFeeds must build the JSON map first, then overlay typed-decoded feeds per key, giving automatic per-key JSON fallback (ADR-0037 Commitment-4). The final Chirp consumer step removes all ~35 JSON fallbacks, the whole-payload KernelUpdate Decodable struct, and ~270 LOC of generic FlatBufferValueDecoder machinery, making the app typed-only. Typed-projection coverage is a v1-blocker; 28 flatc Swift bindings and Android/Kotlin decoders must ship before payload:Value deletion.
