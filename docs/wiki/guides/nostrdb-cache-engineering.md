# Nostrdb Cache Engineering

## nostrdb Cache Engineering

NMP adopts nostrdb cache engineering techniques (visitor query semantics, streaming reads, provenance indexes) as design concepts while keeping NMP's canonical Rust-owned EventStore model, rejecting direct nostrdb dependency. NMP rejects direct nostrdb dependency because nostrdb owns its LMDB environment and write policy, conflicting with NMP's synchronous typed insert outcomes and atomic multi-table transactions. Direct nostrdb adoption is rejected on four decisive grounds (any one sufficient): D4 (nostrdb owns its ingester+writer threads with fire-and-forget process_event), ADR-0011 (no LMDB env-injection seam, blocking single-commit atomicity across sidecars), D8 (composite reverse index naming interested views is inexpressible in nostrdb's flat filter-poll subscriptions; NMP requires per-insert naming of exactly which interested views to wake, which nostrdb's flat filter-poll subscription model cannot express), and licensing (unresolved GPL-vs-BSD ambiguity). The nostrdb-rs Rust binding exposes fold/try_fold on its query iterators, making an early-stopping no-full-buffer scan expressible without forking. A license checkpoint (§5b) blocks code-level borrowing from nostrdb/nostrdb-rs until the GPL-3.0-or-later (crate metadata) vs BSD (C repo) ambiguity is resolved with upstream in writing; no nostrdb source copy (GPL-marked) is permitted in NMP. Adopting design concepts (lessons) is not blocked by the license ambiguity—only verbatim or derived source copying is gated. No native shells own cache policy. There is never a second LMDB writer (ADR-0011 single-writer discipline). NMP keeps the hand-rolled LmdbEventStore targeting nostr-lmdb per ADR-0011; nostrdb-rs is rejected as a dependency. PR #1526 (issue #1515) refreshed the nostrdb adoption decision docs: corrected the stale visitor claim in 3 locations, added a license checkpoint §5b, updated decisive reasons from 3 to 4, replaced §8 prose with an issue cross-reference table, and updated the lessons doc §2.5 and §7.

## Sub-Issue Execution Order

The 9 sub-issues of epic #1523 are worked in order: #1515 (decision docs refresh), #1522 (baseline capture), #1517 (StoreQuery audit), #1516 (streaming query_visit), #1518 (relay provenance indexes), #1519 (projection metadata sidecars), #1520 (event-driven wakeups), #1521 (LMDB diagnostics), #1524 (acceptance gates). Baseline capture (#1522) is a hard precondition before #1516 or any performance-affecting PR. #1516 (streaming LMDB query_visit) and #1518 (relay provenance indexes) are implemented in parallel. Persisting insert-owned projection metadata sidecars (#1519) requires the writer model to be accepted first. Event-driven store notification/replay wakeups are used, with no polling. The evaluation doc §8 Follow-ups is replaced with an explicit issue-to-technique cross-reference table mapping issues #1515–#1524 to the specific nostrdb techniques they implement. The nostrdb-notedeck-lessons doc §2.5 and §7 carry a Resolved (2026-06-18) banner stating that nostrdb-rs is rejected and superseding text clarifying that the earlier 'Option A is probably right' lean and 'depend on it, not reimplement it' recommendation are superseded. All StoreQuery types are reachable via nmp_core::store::{...} (re-exported from nmp_store). The StoreQuery audit (#1517) found all 6 variants have explicit 1:1 LMDB index mappings; uncovered cases (empty kinds, multi-tag intersection, event-ids-only, unrecognized tag keys, text/search) are intentional and documented. KindDtag.d_tag is Vec<u8>, not String — the issue text is wrong on this point. Etag and Ptag queries carry no time cursor (since/until) — intentional conservative over-serve, relay fills the tail. Shapes with empty kinds are rejected by cache-serve query planning (no safe bounded index) and marked served immediately with no store scan attempted. Once a shape's completion key is recorded in served_interest_shapes, re-compilation (relay reconnect, follow-list change) does not re-serve that shape—only new shape hashes are queued. Watermark flooring for shapes not covered by cache-serve is forbidden per ADR §6. The existing relay provenance index (V-52 nmp-relay-index, list_events_seen_on) covers events-seen-on-relay; modifying it for the privacy gate is out of scope as it would be a behavior change to a shipped surface. The new #1518 work adds a relay×kind counted index (nmp-relay-kind) with a presence schema keyed as relay_url||0x00||kind(4 BE)||event_id(32) and empty value; counts are derived via range-count, not a separately-mutated counter, so the index is always rebuildable from provenance and cannot drift. A privacy gate excludes kinds 4, 13, 14, 15, 1059, and 1060 (NIP-04/17/59 private) from the relay-kind index at write time, so private events physically cannot enter the index; the read path also skips them defensively, and the delete path is unconditional so no asymmetry arises. The provenance::delete path recovers kind by storing it redundantly in the relay-kind key, so delete is self-sufficient without an extra event load; kind is threaded as a u32 parameter to provenance::delete. The relay-kind provenance index is maintained only inside provenance::upsert and provenance::delete, never mutated independently, satisfying D4 single-writer-per-fact. NMP_ADDITIONAL_DBS is bumped from 10 to 11 to accommodate the new nmp-relay-kind sub-database. A one-time backfill of the relay-kind index from provenance runs on open for pre-#1518 databases, gated by a domain-versions key; it skips private kinds. Signature changes to provenance::upsert and provenance::delete (adding relay_kind + kind params) require updating every call site in insert.rs, delete.rs, gc.rs, and insert_kind5.rs in one pass. All relay-kind index mutations occur inside the caller's existing RwTxn — no second transaction is opened in the write path (ADR-0011 single-writer discipline). Streaming query_visit (#1516) uses lazy per-row conversion via run_filter_visit; ControlFlow::Break stops immediately without converting further rows. A tie-group buffer preserves (created_at DESC, id ASC) ordering. The implementation was split from query.rs into query_streaming.rs to satisfy the 500-line file-size hard cap. The LMDB fork's BTreeSet-backed iterator already delivers (created_at DESC, id ASC) natively — the old run_filter post-sort was a no-op, making tie-group buffering in the streaming path simpler than anticipated. A test-only AtomicUsize conversion counter (CONVERSION_COUNT) in query_streaming.rs tracks how many rows run_filter_visit converts; it is gated #[cfg(any(test, feature = "test-support"))] (not just #[cfg(test)]) so integration tests in nmp-testing can reach it via the nmp-core test-support feature chain. A Mutex serializer in the test file prevents false failures from parallel tests sharing CONVERSION_COUNT. The early-stop materialization regression gate for #1524 uses the CONVERSION_COUNT instrumented counter, asserting events-scanned ≤ limit+ε after #1516 lands. Latency, allocation bytes, and projection update cadence are machine-sensitive and report-only on PRs (not hard CI gates); events-scanned count and replay-chunk count are deterministic and safe as hard gates. The cache_no_materialization_gate test must prove that query_visit with a Break-at-N visitor causes exactly N conversions, not the full corpus, across all six StoreQuery variants.
