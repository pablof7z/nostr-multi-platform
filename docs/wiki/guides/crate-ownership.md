# NMP Crate Ownership and Helper Policy

## Platform Shell vs. Rust Core Boundary

Anything a second platform would have to reimplement to stay correct — relay choice, signer choice, tag mutation, publish retry, queue truth, nav meaning — belongs in Rust, not in platform shells. Widgets, AppIntents, CarPlay, and Live Activities must not own parallel queues or publish models. <!-- [^3c942-39fb3] -->

## Downstream App Requests

A request from one app is evidence, not permission to specialize the framework; do not add app-named helpers, bespoke publish/read commands, hard-coded product defaults, operator policy, compatibility shims, or quick shared-crate workarounds just because a consuming app needs them. NMP does not require a bespoke write door per event kind: a kind is data, not a code path. What varies is who owns the kind and how it is routed, while signing is uniform. An app inventing its own kind (e.g. kind 232123) with its own tag schema declares it as an app-owned product feature at its composition root, registering its own ActionModule; NMP never learns what the kind means — it just signs and routes it. <!-- [^898a4-d80b6] -->

## NMP Crate Ownership and Helper Policy

NMP crates (crates/) provide reusable Nostr infrastructure that any Nostr application, or a meaningful subset of Nostr applications, could use directly. The ownership test for where a feature lives is: 'would this crate be useful to a completely different Nostr app?' If yes → NMP crate; if app-specific proprietary domain → app crate. App Rust crates (apps/<app>/) hold the Rust side of features specific to that application's domain that would not generalize to other Nostr apps; NMP does not accumulate app-specific logic. The line for crate placement is not protocol vs. product but generic Nostr building block vs. this app's proprietary domain — a product-level feature like NIP-29 group chat belongs in an NMP crate if other Nostr apps would use it. Protocol-owned reusable projections like follow-list live in nmp-nip02, not app FFI crates. New NMP crates must not read as generic 'buckets': an L4 crate such as nmp-wallet should cite a concrete precedent like nmp-note-feed to show the reusable composition it provides. A concept that spans multiple NIPs lives in its own concept crate rather than a doorway inside a single-NIP crate: `nmp-replies` is a standalone concept crate (not a doorway inside nmp-nip01/nip22) because the replies concept spans NIP-10 kind:1 and NIP-22 kind:1111, so a doorway inside nip01 would force a nip01→nip22 dependency. A new shared crate `nmp-wellknown-http` consolidates the bounded-GET + SSRF `host_guard` logic for `.well-known/nostr.json` fetches that was previously duplicated in nmp-nip05 and nmp-nip57, eliminating the forked security-critical code. The `nmp-wellknown-http` crate is classified at layer L1 in the Rule E crate-layer map as a network-transport utility depended on only by L4 protocol crates. The `nmp-wellknown-http` shared crate sets `redirects(0)`, so nmp-nip57 no longer follows redirects — a security hardening side-effect of the consolidation. NIP-AD lives in a new crate `nmp-nip-ad`, sibling to nmp-nip05, following the one-crate-per-NIP convention. The nmp-wallet crate is a new Layer-4 composition crate registered as L4 in rule_e.rs and crate-boundaries.md; it owns the wallet operation journal and wallet reducer. Because its actions are not shippable yet, nmp-wallet is classified as a `[[public_crates]]` entry in `release/nmp-release.toml`, moved from `[[private_packages]]` without waiting for Wave C functional wiring; the entry includes an inline comment citing #2864/#2882/nutsack B1, stating pre-1.0/unstable status and git-rev-off-master pinning, and noting Wave C is still pending. (Previously: nmp-wallet was classified as a `[[private_packages]]` entry, excluded from the v1 release train, rather than an active workspace member.) The `nmp-wallet` `[[public_crates]]` classification only mechanically requires workspace-inherited `version`/`edition`/`license`/`repository`, a `description`, `publish != false`, and a passing `cargo package -p <crate> --list` — it gates packaging/consumability, not functional wiring. The established norm for public crate classification in this project permits 'public + pre-1.0/unstable + functionally incomplete' crates, as set by the precedent of `nmp-nip60` being un-parked via #2865 while still Phase-0-only. The `nmp-wallet` crate owns the event-sourced confluent reducer: state is the fold, the causal trail is a bounded in-memory ring plus a per-atom cause index over the same facts, the saga feeds facts in as a producer, and `kind:7376` is the durable tier — all separate from the money-safety journal's persisted at-most-once records. If a second durable saga ever appears in the workspace (nmp-marmot's pending-MLS-autopublish is the likely candidate), a generic saga substrate should be extracted post-hoc at that point, not built speculatively for the wallet journal. Crate names and ownership assignments must match the actual workspace: the pure NWC codec crate is nmp-nwc, distinct from nmp-nip47. The `nmp-nip47` crate owns the `WalletPaymentPort` implementation (`WalletPaymentPort`) per crate-boundaries §8; `nmp-wallet` does not own or reassign `PaymentPort` itself, it only selects which backend the port routes to. The PaymentPort seam in `nmp-nip57` already emits `PaymentIntent` through `nmp_core::substrate::PaymentPort` with no `nmp-nip47` dependency. The nmp-nip47 and nmp-wallet crates both hold claims on the action scope `{action, nmp.wallet.pay_invoice}` but using different claim_types (mechanism vs. namespace), which produces different linker collision symbols, so the ownership audit does not flag this as a cross-crate collision. The correct resolution is for nmp-nip47 to rescind its exclusive claim on the action scope whose namespace it no longer owns — rescoping to a runtime/mechanism scope (`{namespace, nmp-nip47}`) as nmp-nwc does — leaving nmp-wallet the sole exclusive owner of that action namespace. The nmp-nip60 crate is an active workspace member that inherits workspace package fields and is covered by the `cargo nextest run --workspace` CI command. (Previously: nmp-nip60 was genuinely parked in the workspace `exclude` set.) NMP has no deprecation or backwards-compat anywhere; `#[deprecated]` is itself a violation to be deleted on sight, not a transitional state. No compat aliases — ever: design docs must not bake in compat-alias migrations, and a given port or method must not be listed as both canonical and an alias. The Product Surface section states 'no compatibility aliases' and the shipped test enforcing this is `no_action_namespace_is_duplicated_as_a_compatibility_alias`. `pay_invoice` was untouched in the compat-alias hard-break because it is already the single canonical name per the design doc, not an alias pair. Port ownership assignments must agree with the durable crate-boundaries spec rather than silently reassigning a port (e.g. WalletPaymentPort) away from its designated crate (e.g. nmp-nip47). Terminology must be consistent: use 'composition root' (not 'composition owner') when referring to the wiring location for app-owned features, and every declared dependency must be justified or dropped. The nmp-core crate must remain free of wallet/NWC/mint/Cashu nouns; the 74 hits for banned terms are all boundary-explaining comments and payment.rs is protocol-neutral, which must be preserved. `nmp-core` must learn no Cashu/nutzap/NWC/mint nouns. `nmp-native-runtime`'s per-NIP dependencies are gated behind `optional = true` / feature flags, with the end state of zero per-concept deps so omitting a concept crate means its symbols don't exist at any layer. A doctrine-lint rule `feed_vocabulary` is a token-ban ratchet scoped to `nmp-native-runtime`, `nmp-uniffi-support`, `nmp-browser-runtime`, and the `nmp-codegen` feed-helper templates, with internal vocabulary (`FeedSessionRegistry`, `FeedSessionId`, `Nip50SearchSession`, `Nip29Group*Session`) explicitly never flagged. Live workspace member crates contain an `ownership.rs` module with a `declare_crate_ownership!` descriptor covering all NIP kinds they implement; `nmp-nip60` includes a descriptor covering all 7 NIP-60/61/88 kinds. The `nmp-nip60` ownership descriptor identifies the crate as the 'Cashu backend adapter for the `nmp-wallet::WalletBackend` seam', with notes deferring journal/seam/selection to nmp-wallet. The `nmp-nip60` crate is classified as a public crate in `release/nmp-release.toml`. Within `nmp-nip60`, kind:17375 relay tags are demoted to a clearly-named non-authoritative `legacy_relay_hint` field/accessor, with doc comments stating that kind:10019 + NIP-65 fallback is the authoritative relay source (owned by `nmp-wallet`); the `nmp-nip60` Phase-0 cleanups (#2870) include killing the `legacy_relay_hint`→authoritative kind:10019 relay leak as an explicit Phase-1 blocker. The NIP-61 `NutZapInfo.relays` field is authoritative per design and left untouched. Acceptance criteria for `nmp-nip60` reactivation include `cargo test -p nmp-nip60` (10 tests + 2 doctests), `cargo test -p nmp-testing --test doctrine_lint_smoke` (203 tests), `cargo build --workspace`, `ci/check-release-manifest.sh`, and `cargo package -p nmp-nip60 --list` all passing clean. Every internal `nmp-*` path dependency must carry a `version =` field for crates.io publish resolution; dev-dependencies with a bare `path` (no version) are exempt because cargo auto-strips them during packaging. The 62-crate topological publish order for the `1.0.0-rc.1` release starts with `nmp-ownership → nmp-codegen → nmp-component-registry → nmp-coverage-gate → nmp-kinds → …` and ends in `nmp-testing, nmp-uniffi-support`.
