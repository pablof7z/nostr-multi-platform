# Mailbox Cache

## MailboxCache

NIP-owned caches (DmRelayCache, MailboxCache, ProfileCache) are derived projections that distill events into compact query-shaped fast indexes; the kernel reads them back through narrow capability traits (DmInboxRelayLookup, etc.) without knowing what kind produced the data, and on restart they are rebuilt from the authoritative store, which is why the authoritative store must be a complete log — a relevance-shaped hole in the store becomes a permanent hole in every derived projection that replays from it; if a kind's events were dropped at ingest, its cache can't be rebuilt after restart, which is the mechanism behind recurring 'missing DMs' findings. They follow a CQRS/read-model pattern: parsers write derived facts into typed caches at ingest time, and the kernel reads them back through narrow capability traits without knowing what kind produced the data. The NMP kernel does not proactively fetch kind:10002 (NIP-65 relay lists) for third-party authors; it only fetches kind:10002 for the active/logged-in account at startup. The outbox router (nmp-router GenericOutboxRouter with 7 lanes) routes kind:0 queries to an author's NIP-65 write relays (Lane 1), but it is inert for third-party profiles because the kernel never proactively fetches kind:10002 for any author other than the active/logged-in account. When the author's kind:10002 is not cached, kind:0 profile queries fall through to operator indexer relays only (Lane 6/7), never to the author's own NIP-65 write relays. If no relay carries the indexer role in the app configuration, zero kind:0 REQs are sent for any third-party author. The MailboxCache (which feeds the outbox router's Lane 1) is written only by Kind10002Parser ingesting kind:10002 events that happen to arrive on the wire; nothing proactively fetches kind:10002 for the follow set or encountered authors. The kind:10002 discovery fetch for third-party authors targets indexer_relays ∪ app_relays (deduplicated), so that switching primal to a non-indexer role does not regress relay-list discovery. Measured protocol-level profile resolution: the indexer-only baseline was 10.2% (108/1054) when purplepag.es was AUTH-walled, rising to 27.9% (294/1052) when it answered. The outbox model (indexers ∪ authors' own write relays) reached 50.0% (528/1054) and 60.3% (635/1052) respectively. purplepag.es AUTH-gates and rate-limits connections, returning AUTH + CLOSED responses that can cause profile REQs to silently fail; it AUTH-walls anonymous bulk queries, making the effective indexer baseline dependent on relay availability, while the outbox mechanism's contribution remains steady regardless of indexer health. The relay admission/health backoff system can silently shrink the indexer lane if relays get marked inadmissible. The ensure-10002/relay-list acquisition behavior must be intrinsic to the single routing-infrastructure layer that every authors-filtered interest funnels through, with zero relay-list awareness in feature code; it must NOT be placed on higher-order callers like the follows feed or profile claim. The subscription recompile chokepoint (subs/recompile.rs, SubscriptionLifecycle recompile_and_diff_with_lookup) already implements intrinsic per-author kind:10002 discovery: when any authors-filtered interest is registered, the chokepoint automatically (a) routes the REQ to app_relays/indexer fallback immediately so the feed is never blank, (b) emits a batched kind:10002 probe for uncached authors to indexers, and (c) re-routes to each author's own write relays when their kind:10002 arrives via Nip65Arrived. For any author-scoped subscription (any authors:[...] REQ), if the author's kind:10002 is uncached, NMP immediately routes the REQ to app/indexer relays as fallback (never a blank feed), then re-routes to the author's own relays once their 10002 arrives — progressive enhancement. When a kind:10002 arrives for an author whose profile was previously unresolved, the Nip65Arrived recompile trigger automatically re-routes the registered kind:0 interest from indexer fallback to the author's write relays, replacing the bespoke refresh_profile_after_mailbox function. nprofile TLV relay hints from NprofileData.relays must be threaded into the profile claim interest's hints as HintSource::UserConfigured, so authors whose 10002 is on no indexer still resolve from their nprofile-embedded relay. Greedy weighted max-coverage set-cover relay minimization exists in selection.rs and runs on every recompile, reducing relay fan-out to bounded select_max_connections/select_max_per_user. The mailbox-discovery probe set uses an epoch mechanism: probed_mailboxes is re-armed only on a genuine down-to-up recovery of the indexer lane, not on per-socket reconnects or sibling-still-live flaps; adding a probe lifecycle is Workstream B3. The probed_mailboxes clear is gated to genuine reconnects (where the socket was previously down, using indexer_socket_was_down) and new-indexer-added, not every initial connect, preventing feed subscription churn and re-REQ storms that would break the web feed rendering during initial relay connection. NIP-17 DM inbox uses LogicalInterest with PTagRouting::Nip17DmRelays and is fail-closed (emits no subscription if kind:10050 is not cached, rather than falling back to bootstrap relays); NIP-57 zaps use LogicalInterest registration exclusively and have zero bespoke REQ building. claim_event correctly registers a LogicalInterest via OneshotApi and flows through the planner's compilation path, inheriting the D3 mailbox-probe discovery and NIP-65 outbox routing — it does not have the bespoke bypass defect. NIP-60 wallet fetches NIP-65 lists from hardcoded wss://purplepag.es, bypassing the kernel's D3 outbox router (minor, low-impact since it only affects the self-account's wallet cold-start; follow-up filed as #1434). The NMP transport pool dials arbitrary relay URLs on demand (not just configured relays) with RelayConnectionKind::Temporary and 60-second idle teardown, so connecting to third-party author relays from their kind:10002 requires zero new transport capability.
