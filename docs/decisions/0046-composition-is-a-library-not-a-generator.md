# ADR-0046: Composition is a library, not a generator

Status: ACCEPTED (owner-approved 2026-06-12)

> Numbering note: `0045` is the highest decision in `docs/decisions/` (there is
> a known `0041` duplicate, both accepted). This ADR takes the next free
> number, `0046`, per the repo's single-source-of-truth / no-duplicate-id
> discipline.

## Context

Three artifacts occupied the "how does a downstream app compose NMP?" question,
and they answered it two incompatible ways.

1. **The composition-root library** (`nmp-app-template`, now renamed — see the
   Decision). A single function, `register_defaults(&mut impl AppHost)`, wires
   the canonical NMP composition in one call: the NIP-01/02/17/57/65 action
   modules, the production routing substrate (`GenericOutboxRouter` +
   `InMemoryMailboxCache`), the DM-inbox + zap-receipts + WOT runtime
   controllers, the indexer-republish policy, the D2 coverage hook, and the
   NIP-23 long-form typed projection. This is the Bevy-`DefaultPlugins` /
   Spring-Boot-starter shape: depend on the framework's default composition and
   call it.

2. **The `nmp-codegen gen modules` scaffolder.** Given an `nmp.toml` manifest,
   it generated a per-app `nmp-app-<name>` FFI crate
   (`action`/`capability`/`domain`/`envelope`/`ffi`/`lib`/`update`/`view_spec`
   modules). This is the create-react-app **eject** shape: generate a wiring
   tree the developer then owns.

3. **`apps/fixture`** (`nmp-app-fixture` + `fixture-todo-core`), the lone
   consumer of (2).

**Every real consumer chose the library.** Chirp calls
`nmp_app_template::register_defaults` at
`apps/chirp/nmp-app-chirp/src/ffi/register.rs:108`. The gallery composition root
(`apps/nmp-gallery/nmp-app-gallery`) is a thin wrapper that does nothing but
forward to it. The external podcast-player pins and composes the library crates
the same way (`docs/architecture/external-consumers.md`). Not one real app was
ever generated by `gen modules`.

**The generated shape was structurally non-functional, and its only consumer was
manufactured circularly.** Historically the generated `FfiApp` (in the
since-deleted `apps/fixture` tree) constructed an `NmpApp` but never called
`register_defaults`, never installed routing, and never registered any NIP action
module — so a generated app could not publish, follow, DM, zap, resolve outbox
relays, or render long-form; meanwhile `apps/fixture` existed only to give the
otherwise-orphan generator a test target, guarded by a `fixture_zero_diff`
zero-diff CI gate (both the fixture tree and that gate are now removed). With
PD-033-A closed by the external consumers (`win-the-day`, `hl`, podcast-player —
`docs/architecture/external-consumers.md`), the fixture's last arguable role —
"a second app proving the thesis" — is also gone; a generated non-functional app
proved nothing about the framework thesis anyway.

## Decision

**There is one mechanism for composing NMP: the composition-root library.**

- A downstream app depends on the composition-root library and calls
  `NmpAppBuilder` + `register_defaults`. This is the framework's *default
  composition*, the Bevy-`DefaultPlugins` / Spring-Boot-starter pattern.
- There is **no FFI-crate generator**. A downstream app is a thin shell that
  CALLS the library: a `<name>-core` crate that depends on the composition-root
  library and whose `register` forwards to `register_defaults`, driven through
  `NmpAppBuilder`. The app owns **no framework wiring of its own** — it inherits
  it from `nmp-defaults`.
- **`gen modules` and `apps/fixture` are deleted.** The generator
  (`generate.rs` / `ffi_gen.rs` / `workspace.rs`), the `modules` subcommand, the
  `fixture_zero_diff` / `ffi_dispatch` / module-determinism tests, the
  `gen-modules` justfile targets, and the `apps/fixture` tree are removed. The
  `nmp.toml` manifest parser survives because `nmp doctor` / `nmp upgrade` (the
  dependency-policy commands) read it; the Swift `gen swift` / `gen
  typed-decoders` emitters survive untouched because they gate live CI
  (`.github/workflows/codegen-drift.yml`).
- **The library is renamed to tell the truth.** `nmp-app-template` →
  `nmp-defaults`. "Template" implies copy-and-edit; the crate is a runtime
  composition-root library you depend on and call, not a template you fork.

### Why there is no FFI-crate generator

The generated FFI crate was the eject tree. Under this decision the developer
never owns framework wiring — they inherit it from `nmp-defaults` and add only
their app-specific modules on top of `register_defaults`. A downstream app is
therefore just: a `Cargo.toml` pinning the NMP crates, a `register` shell that
calls `register_defaults`, and an example that runs it. No generator emits any of
this. The bindings story is unchanged by this ADR (see "Relation to M14/ADR-0030"
below).

## Prior art

- **Bevy `DefaultPlugins`.** A Bevy app calls
  `App::new().add_plugins(DefaultPlugins)` — a library call that installs the
  engine's standard plugin set. Bevy does not *generate* a per-app engine; you
  depend on the defaults and add your own plugins. `register_defaults` is
  NMP's `DefaultPlugins`.
- **Spring Boot starters.** A Spring app adds a `spring-boot-starter-*`
  dependency and auto-configuration wires the beans at runtime. You do not run a
  generator that emits Spring's wiring into your source tree.
- **Rails: thin scaffold over railties.** `rails new` scaffolds a thin app that
  *depends on* the framework's railties; it does not copy Rails' internals into
  your app. An NMP app is exactly this shape — a thin shell over the
  `nmp-defaults` library.
- **create-react-app `eject` — the cautionary tale.** CRA's `eject` copies the
  framework's build/wiring config into your repo, and you own it forever; the
  community consensus is "don't eject." `gen modules` was NMP's eject: it emitted
  a wiring tree the developer owns — except it emitted a *non-functional* one
  (no `register_defaults`), which is eject's downside with none of its upside.

## The steelman, and why it is rejected

**Steelman:** "A generator gives a typed, app-specific surface (closed
`AppAction`/`AppUpdate` enums, per-app `FfiApp`) that a runtime library call
cannot — that is real value worth keeping."

**Rejection:** the runtime registry already provides exactly the extensibility a
generated arm would, without a generator:

- Action dispatch is a **runtime registry keyed on namespace strings**
  (`nmp_app_dispatch_action(app, namespace, action_json)`), backed by a
  `HashMap<String, …>` in `nmp_core::kernel::action_registry`. Registering a
  module is a library call (`AppHost::register_action::<M>()`); dispatching is a
  string-keyed lookup. **Chirp wires NIP-29 group chat, the wallet, zaps, and
  the OP-feed with zero generated match arms** — every one of them through this
  runtime seam on top of `register_defaults`. The generated closed enum bought
  nothing Chirp needed.
- Post-UniFFI (M14 / ADR-0030), the *bindings* are codegen — but **wiring stays
  a library.** The thing a generator would have produced (the FFI wiring crate)
  is precisely the thing that was non-functional; the thing that is legitimately
  generated (typed bindings) is unaffected by deleting `gen modules`.

So the generator's claimed unique value (a typed app surface) is delivered by
the runtime registry + the bindings codegen that survive — and the generator's
actual output (un-wired FFI tree) is a liability, not an asset.

## Consequences

- **One composition mechanism.** "How do I compose NMP?" has exactly one answer:
  depend on `nmp-defaults`, call `register_defaults`. No second, non-functional
  path to mislead a new builder.
- **The rename ripples through the repo.** `nmp-app-template` → `nmp-defaults` in
  the workspace member list, every dependent `Cargo.toml`
  (`nmp-app-chirp`, `nmp-app-gallery`, `nmp-testing`), every
  `nmp_app_template::` Rust path, the release manifest, and the docs. Decisions
  0036–0039 (which named `nmp-app-template`) carry a one-line "renamed to
  `nmp-defaults` by ADR-0046" annotation rather than a history rewrite.
- **External-consumer coordination.** Consumers that pin `nmp-app-template` by
  git rev (podcast-player) must update the **dependency name** to `nmp-defaults`
  when they bump their rev, alongside the usual rev bump. `hl` (path-dep) updates
  its path. This is a breaking rename; see `CHANGELOG.md` and
  `docs/architecture/external-consumers.md`. The orchestrator handles the
  downstream bumps after merge.
- **App composition is simpler and honest.** A downstream app is a thin shell
  that compiles against the live `nmp-defaults`/`nmp-ffi`/`nmp-core` crates and
  runs `register_defaults`. There is no `nmp gen modules` step and no generated
  `apps/` tree. (The codegen CLI's surviving subcommands are `gen swift` and
  `gen typed-decoders` — bindings emitters, not a composition generator.)
- **`aim.md` §4.14's GOAL is unchanged.** The north star — an immediately-
  buildable app — still holds; only the *mechanism* behind it changes (thin
  library shell instead of a generated FFI crate). This ADR does not edit
  `aim.md` (immutable).
- **PD-033-A closure removed the fixture's last legitimate role.** The "second
  app proving the thesis" justification is satisfied by the external consumers;
  a generated non-functional fixture never satisfied it.

## Refinement: tier split + config struct (2026-06-12, Bevy/Spring study)

`register_defaults` historically fused two layers with different audiences. The
[Bevy `DefaultPlugins` study](https://docs.rs/bevy) (validated by Spring Boot 4's
modularization retrospective) motivates separating them — `DefaultPlugins` vs
`MinimalPlugins`, and `.set(WindowPlugin { .. })` config-as-fields.

**1. Tier split — `register_substrate` (the `MinimalPlugins` analog).**
`nmp-defaults` now exposes `pub fn register_substrate(app: &mut impl AppHost,
gate: CoverageGate)` — the **substrate correctness** tier, called unconditionally
by `register_defaults`:

- `nmp_router::register_actions` (the `nmp.nip65.publish_relay_list` action — the
  routing crate's own action, inseparable from the routing substrate it publishes
  for; NOT a social toggle),
- the shared `Arc<InMemoryMailboxCache>` + mailbox-cache reader + routing factory
  + kind:10002 parser (one cache, three clones),
- the publish-resolver factory,
- the raw-event forward / republish policy,
- the `CoverageGate` coverage hook + the NIP-77 negentropy runtime (one shared
  gate value feeds both collaborators).

Without this tier the app is **broken, not minimal**: routing returns
`Unroutable`, `PublishTarget::Auto` fail-closes to `NoTargets`, kind:10002 never
populates the mailbox cache, oversized relay plans are never trimmed. It is
correctness, so it is never toggleable.

**Why this is callable, not a comment block.** The non-social external consumers
(`podcast-player`, `hl`, `win-the-day` —
`docs/architecture/external-consumers.md`) want the routable substrate **without**
the social bundle. Before the split they had two bad options: call
`register_defaults` and swallow the social bundle, or hand-copy the substrate
block — which is *un-copyable* because it threads a single shared
`Arc<InMemoryMailboxCache>` through three seams; copy it wrong and the writer
(parser) and readers (router + NIP-19 encoder) desync. That is the V-48 failure
mode this crate exists to prevent, so the substrate tier is now a function they
call.

Reducer-owned delivery roots that cannot implement the full AppHost tier
(currently Chirp web) call `nmp-substrate-defaults`, the wasm-safe helper used
by `register_substrate` for the shared router/mailbox/profile/contacts
cache-parser floor. The native `register_substrate` tier still owns the
AppHost-only publish resolver, raw forwarding, coverage, and NIP-11 pieces.

**2. `NmpDefaults` config struct + `register_defaults_with` (config-as-fields).**
`pub fn register_defaults_with(app: &mut impl AppHost, defaults: NmpDefaults)`
consumes a declarative config; `register_defaults(app)` delegates to it with
`NmpDefaults::default()`. The struct fields:

- `coverage_gate: CoverageGate` — **the shared D2/NIP-77 policy.** One value feeds
  the coverage hook AND the negentropy runtime; overriding it post-hoc is
  impossible without desyncing them, which is exactly why it is config here rather
  than a hardcoded `CoverageGate::default()`. A regression test
  (`tests/substrate_coverage_gate.rs`) pins that a custom gate reaches both
  collaborators.
- `nostrconnect_bootstrap_relay: String` — operator-policy NIP-46 fallback relay
  (default `wss://relay.damus.io`). Always wired; its *value*, not its presence,
  is the knob.
- `social` / `dms` / `zaps` / `longform: bool` — the social-feature toggles
  (nip02+WOT / nip17+DM runtime / nip57+zap runtime / NIP-23 typed projection).
  All default `true`, so `register_defaults_with(app, default())` is byte-for-byte
  equivalent to today's `register_defaults(app)` (pinned by
  `tests/register_defaults.rs`).

**Zero behaviour change for `register_defaults()`.** This refinement is a pure
extraction + parameterisation: the registration order, the shared-`Arc`
structure, and every default value are unchanged, so Chirp and every existing
consumer compile and behave identically — `register_defaults` keeps its exact
signature.

A separate, parallel decision (**ADR-0049** — yielding `register_default`
semantics + a composition ledger in `nmp-core`'s action registry) lands
independently; it is orthogonal to this `nmp-defaults`-local tier split.

## Relation to M14 / ADR-0030 (UniFFI bindings)

ADR-0030 / M14 move the **host bindings** (Swift/Kotlin) to generated UniFFI
output. That is orthogonal to this ADR: bindings are a mechanical projection of
a typed surface and are legitimately generated; **composition wiring is a
library call and stays one.** Deleting `gen modules` removes the *FFI-crate
scaffolder*, not the bindings codegen, and does not touch `gen swift` / `gen
typed-decoders`, which remain the live CI-gated emitters.
